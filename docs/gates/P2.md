## Revue des critères

| Critère | Preuve disponible |
|---|---|
| A2.1 — cinq générations, capacité | Docker GPU : 5 Idol COMPLETED, maximum 1 RUNNING, interrogation chaque seconde |
| A2.2 — crash du worker | Docker GPU : SIGKILL après prise pendant chargement, ABANDONED, QUEUED en 73,68 s puis succès ; baux/promotions périmés couverts en tests |
| A2.3 — arrêt propre | Docker : SIGTERM sur Fake HANG, INTERRUPTED, budget inchangé ; le délai d'arrêt permet aussi une fin normale si le job termine pendant la grâce |
| A2.4 — relances transitoires | Docker : OOM Fake, délais 30,086 / 60,065 / 120,064 s, puis FAILED à la quatrième tentative |
| A2.5 — absence d'objet | Docker Fake : une tentative, NO_OBJECT_DETECTED, aucune relance ; classification Idol vérifiée en P1 |
| A2.6 — rétention | Docker CPU à 30 jours ; tests de suppression immédiate simulée par cutoff injecté, protection et RUNNING conservés |
| A2.7 — effacement échoué | Docker CPU non root : PermissionError, marqueur persistant, suppression SQL et disque au cycle suivant après restauration des droits |
| A2.8 — upload | Docker HTTP : 21 Mio → 413, PDF renommé → 415, en-tête 100 Mpx → 422 |
| A2.9 — configuration | Tests de démarrage : variables invalides refusées et nommées dans ConfigError |
| A2.10 — chemins sûrs | Tests stockage/API : ULID, traversées, symlinks et téléchargements reconstruits par identifiant |
| A2.11 — pause | Docker GPU : le job courant termine, quatre suivants restent en file jusqu'à reprise |
| A2.12 — attente VRAM | Tests : pas d'enfant sous le seuil, reprise jusqu'à COMPLETED quand la VRAM revient ; timeout GPU_UNAVAILABLE sans tentative ni relance |
| A2.13 — erreur inconnue | Docker Fake : INTERNAL, needs_diagnosis, une tentative, aucune relance automatique |
| A2.14 — dégradation | Docker Fake : trois erreurs CUDA, même superviseur, pause système, reprise explicite sans redémarrage |
| A2.15 — worker arrêté | API, file NO_WORKER, restitution VRAM et succès après redémarrage démontrés ; **partie UI à reporter à P3** |
| A2.16 — profil GPU | Résolution Compose et Docker CPU : aucun worker ni accès GPU sans profil explicite |

La simulation « zéro jour » utilise une date de rétention injectée pour rendre immédiatement
éligible une génération terminale non protégée. La configuration `STORAGE_RETENTION_DAYS=0`
continue de **désactiver** la purge automatique, conformément à l'architecture ; ce comportement
est testé séparément. Aucun changement de politique de rétention n'est demandé.

Tests complémentaires de la revue :

- `test_queued_job_starts_when_free_vram_recovers` dans `test_supervisor.py` ;
- `test_zero_day_retention_simulated_with_cutoff_preserves_protected_and_running` dans `test_janitor.py`.

# P2.11 — validation Docker GPU

Date : **2026-11-05**. Essais GPU explicitement autorisés, hors entraînement concurrent,
dans un projet temporaire. **Intégration du worker et scénarios ci-dessous réussis.**
Le gate P2 reste soumis à revue et validation de l'utilisateur.

## Banc de validation

- Cible `worker` construite avec les dépendances verrouillées, dont torch 2.14.1+cu132,
  torchvision 0.29.2+cu132 et le commit Idol 4702a7f.
- Image testée : `sha256:cac78dbd3f2073fabd391de9f6aaae026811241e5e8a95ffd94a4d5f4b517530`.
- Projet et tag dédiés, données et cache temporaires, poids existants montés en lecture seule,
  cache inscriptible, réseau désactivé pour le worker. Aucun téléchargement de poids.
- Réservation NVIDIA uniquement sur le worker. API, janitor et migrateur restent sans GPU.
- Mode `full`, preset `fast`, seuil d'admission 8 192 Mio, concurrence globale 1.
- Pour borner les essais : déchargement à l'inactivité après 15 s, grâce superviseur 3 s et
  délai d'arrêt Docker 15 s. Les valeurs publiques par défaut restent 900/90/120 s.
- Les erreurs OOM/CUDA/absence d'objet sont injectées par le FakeAdapter. Les générations Idol
  sont réelles ; les erreurs injectées ne sont pas des fautes matérielles du GPU.

## Résultats

| Critère / scénario | Observation |

| A2.1 — cinq soumissions Idol | 5 COMPLETED, une tentative chacune ; maximum observé : 1 RUNNING, interrogation chaque seconde |
| Admission réelle | Minimum enregistré à la prise pour Idol : 11 163 Mio libres, supérieur au seuil 8 192 Mio |

| A2.3 — arrêt SIGTERM | Fake HANG effectivement démarré, arrêt par Compose : INTERRUPTED, attempt_count=0, sans consommation du budget |
| A2.15 — worker arrêté | API saine, nouvelle image QUEUED/NO_WORKER ; après redémarrage, génération Idol COMPLETED |

| A2.4 — OOM injecté | Quatre tentatives, puis FAILED ; délais mesurés : 30,086 / 60,065 / 120,064 s |
| A2.13 — erreur inconnue | Entrée normalisée corrompue dans le banc : INTERNAL, needs_diagnosis=true, une tentative, aucune relance automatique |

Durées des cinq premières générations, **chargement inclus** : 124,69 / 55,32 / 76,58 / 51,77 /
43,12 secondes. Le premier chargement a pris environ 67,5 s. Ce ne sont pas des mesures
comparables aux temps d'inférence seule du gate P1 : cache initial isolé, première compilation,
et rechargements entre jobs. La politique conservatrice actuelle décharge un enfant résident
si la VRAM libre est inférieure au seuil d'admission avant le job suivant.

Le scénario de dégradation a été rejoué après correction de la synchronisation du **banc de test** :
l'essai initial avait envoyé la première erreur avant la fin du redémarrage demandé, répartissant
les erreurs sur deux superviseurs. L'essai final vérifie explicitement un worker_id identique
pour les trois tentatives et pour le job réussi après reprise. Aucun correctif applicatif requis.

## Nettoyage et portée

Tous les conteneurs et le réseau du projet temporaire ont été supprimés. Les relevés des services
préexistants sont identiques avant/après ; les données persistantes réelles sont inchangées.
Après nettoyage, aucun processus GPU du banc ne subsiste ; seul le processus résident préexistant
reste présent. Poids jamais modifiés, caches de test séparés. Aucun déploiement permanent.

Ces exercices complètent les [preuves CPU](P2.11-cpu.md) et les **505 tests sans GPU** déjà verts
avec Ruff check/format et mypy strict. Le code n'a pas changé pendant les validations Docker.
Les 13 tests GPU historiques de P1 n'ont pas été rejoués comme suite pytest dans cette campagne.

## Points de revue du gate P2

- A2.6 : la rétention est démontrée à 30 jours en conteneur, avec conservation des protégées ;
  les tests unitaires conservent aussi RUNNING. L'architecture définit 0 comme désactivation,
  tandis que le critère mentionne « 0 jour simulé ». La revue a ajouté un test de cutoff injecté
  pour cette simulation immédiate, en conservant la désactivation par la valeur de configuration 0.
- A2.12 (VRAM factice et timeout), A2.9 (configuration invalide), A2.10 (chemins sûrs) sont couverts
  par les tests sans GPU ; ils n'ont pas fait l'objet d'une nouvelle injection en conteneur ici.
- La partie **UI** d'A2.15 ne peut pas être démontrée avant P3. Seule la partie API/file/reprise
  du worker est validée à ce stade.
- Le SIGKILL a été exercé pendant le chargement d'un job RUNNING ; pas après publication des
  résultats. La protection des promotions et baux périmés est couverte par les tests unitaires.
- L'utilisateur doit valider le gate P2 et ces précisions avant de commencer P3.

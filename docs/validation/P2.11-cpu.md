# P2.11 — validation Docker CPU

Date : **2026-11-05**. Validation autorisée sans GPU, sur données temporaires isolées.
**Résultat : build CPU et intégration Compose CPU réussis. Le gate P2 n'est pas validé ici.**

## Périmètre et isolation

- Docker Engine 29.9.2, Docker Compose v5.6.1.
- Résolution du Compose source avec un projet temporaire et sans fichier `.env` local.
  Services sélectionnés par défaut : migrate, api, janitor ; aucun worker GPU.
- Copie de validation des seuls services CPU : tous les bind mounts sous un répertoire temporaire,
  nom de projet et tag d'image dédiés, aucun port publié, restart désactivé pour le banc de test.
  `ENABLE_FAKE_ADAPTER=true` seulement dans cette copie ; le défaut public reste false.
- Image construite avec la cible `api` du Dockerfile et le verrou gelé, sans extra idol.
  Empreinte de l'image testée :
  `sha256:c60a4375fcbe35dc7207b777c9b990d1fa1697b01286b3bc4f640c811066614f`.
- Contexte transmis au build : environ 733 Ko ; données, poids, secrets et historique exclus.
- Aucun DeviceRequest GPU dans les conteneurs, aucun nœud `/dev/nvidia*`, torch absent de l'image.
  Le parcours Fake utilise une mesure GPU **synthétique injectée**, sans appel NVML ni inférence GPU.

## Résultats observés

| Vérification | Résultat |
|---|---|
| Résolution réelle par Compose | Configuration acceptée |
| Build de l'image CPU | Réussi, dépendances verrouillées, package installé |
| Migration initiale | Sortie 0, schéma à head, 5 tables métier + alembic_version |
| Migration répétée | `alembic upgrade head` réussit une seconde fois |
| Échec volontaire du migrateur | Sortie 23 ; API et janitor restent créés sans démarrer |
| Santé au démarrage et après restart | API et janitor healthy |
| Exécution non root | UID 1000, rootfs réellement en lecture seule |
| Montages persistants | Écriture autorisée dans les seuls répertoires de données |
| Promotion inter-montages | EXDEV observé entre tmp et sources ; upload et résultats promus correctement |
| Upload → file → Fake | Vrai processus spawn CPU, génération COMPLETED, métriques et progression |
| Artefacts | Trois artefacts ; SHA-256, Range 206 et ETag vérifiés via HTTP |
| Journaux | Événements de progression et issue SUCCEEDED lus via `/logs` |
| Suppression manuelle protégée | Réponse 204, lignes et répertoires supprimés |
| Erreurs d'entrée réelles HTTP | PDF renommé : 415 ; paramètres invalides : 422 ; en-tête 100 Mpx : 422 ; fichier 21 Mio : 413 |
| Actions de file | Annulation, relance manuelle et suppression réussies |
| PENDING ancien complet | Repris en QUEUED par la boucle du vrai conteneur janitor |
| PENDING ancien incomplet | FAILED / INGEST_FAILED par cette même boucle |
| Bail expiré | Tentative ABANDONED, génération remise en file, journal de reprise corrélé |
| Bail expiré avec annulation demandée | Tentative/génération CANCELLED, sans perte de l'annulation |
| Suppression dont l'effacement échoue | PermissionError non root, marqueur conservé, suppression effective au cycle suivant après restauration des droits |
| Rétention au redémarrage du janitor | Terminal ancien non protégé supprimé ; protégé conservé |
| Persistance après restart | Données bind-mountées conservées, suspension de distribution conservée |

Le marqueur deleting_at rend déjà la ressource invisible en HTTP. La reprise de suppression a
été vérifiée jusqu'à disparition **de la ligne SQL et du répertoire**, au-delà du seul 404.

Les vérifications du backend préparatoires restent : **505 tests sans GPU**, Ruff check/format
et mypy strict verts. Aucun changement du code applicatif n'a été nécessaire pendant cette
validation Docker. Les vérifications de conteneur ci-dessus sont des exercices d'intégration
séparés de ce compteur pytest.

## Nettoyage et limites

Les deux projets temporaires (parcours nominal et échec de migration) ont été arrêtés et
supprimés, avec leurs réseaux. Aucun prune global ni arrêt d'un service préexistant.
Les données réelles du projet sont restées inchangées. L'image de validation et les relevés
locaux peuvent être conservés pour examen.

Restent à réaliser avec autorisation GPU : construction/test de l'image worker, accès aux poids
hors ligne et au cache, admission réelle, générations Idol, signaux/arrêt et restitution VRAM,
reprise après crash et critères A2 du [plan](../development-plan.md). Cette validation CPU ne
remplace ni ces essais ni l'approbation du gate P2 par l'utilisateur. Aucun déploiement permanent.

Suite : une [campagne GPU](P2.11-gpu.md) autorisée a été réalisée ensuite, avec construction du
worker, générations Idol, arrêts/reprises et erreurs injectées. Elle ne remplace pas la revue du gate P2.

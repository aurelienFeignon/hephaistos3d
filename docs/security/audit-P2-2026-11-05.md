# Audit de sécurité P2 — avant P3

> État historique avant correction. Voir les [corrections et preuves](remediation-P2-2026-11-05.md)
> pour la résolution des constats SEC-01 à SEC-05.

Date : **2026-11-05**. Référence de code : **2de0373**. Audit demandé après validation
fonctionnelle de P2 par l'utilisateur. Aucun correctif applicatif appliqué pendant cet audit.

**Conclusion : conserver le backend isolé. Avant publication du frontend/proxy P3, traiter
la frontière HTTP (accès, origine, Host) et les limites globales de ressources.** Aucun exploit
critique à distance n'a été démontré dans la topologie actuelle, où Compose ne publie aucun
port. Ce constat n'est pas une certification d'absence de vulnérabilité.

## Périmètre et méthode

Revue manuelle : API, multipart, normalisation d'images, stockage, baux/publication/suppression,
janitor, journaux, configuration Compose/Dockerfile, CI et routes frontend P0 existantes.
Reproductions avec TestClient, base SQLite migrée et fichiers temporaires uniquement.
Pas de scan réseau, attaque sur un service existant, saturation, build Docker, changement de
paquet ni exécution/inférence GPU.

Outils : pip-audit sur exports figés, npm audit sur package-lock, Bandit sur les sources Python,
recherche de motifs de secrets dans les fichiers suivis, vérification de l'avis primaire npm.
Les reproductions ci-dessous emploient des images synthétiques, sans données personnelles.

## Constats et priorités

### SEC-01 — frontière HTTP absente pour un service exposé — élevée avant P3

Sources : `backend/src/hephaistos/api/dependencies.py:11`, `api/app.py:128`,
`api/uploads.py:81` ; absence de filtrage Host/Origin dans la factory.

`current_principal()` retourne toujours le principal local, sans authentification. C'est un
choix connu du MVP, actuellement compensé par le réseau interne et l'absence de port publié.
Toute personne pouvant atteindre l'API dispose donc des mêmes droits de lecture, création,
annulation et suppression, ainsi que de l'accès aux sources et journaux.

Preuves bornées :

- PUT dispatch avec `Host: untrusted.example` : **200**, état effectivement changé.
- POST multipart image avec `Origin: https://untrusted.example` et
  `Sec-Fetch-Site: cross-site` : **201**, génération créée sans justification d'accès.

La reproduction prouve le comportement du serveur ; elle ne démontre pas un exploit complet
dans un navigateur. Les restrictions réseau privé et autres politiques varient selon navigateur
et contexte. L'absence de CORS n'est pas une autorisation d'accès et ne doit pas être considérée
comme une protection suffisante des soumissions multipart.

**À faire avant exposition HTTP** : définir le mode personnel local et le mode LAN, filtrer
Host et Origin attendus, rejeter les mutations cross-site, mettre en place une protection CSRF
adaptée aux soumissions et au proxy. Pour un accès LAN ou partagé, ajouter une vraie
identification/session ou un mécanisme d'accès explicite. Conserver API interne et liaison du
frontend à localhost par défaut. Prévoir les tests négatifs correspondants avant branchement UI.

### SEC-02 — absence de budget global d'entrée et de stockage — élevée si API accessible

Sources : `api/uploads.py:81`, `api/uploads.py:157`, `api/app.py:144`,
`imaging.py:61`, `compose.yaml` (limites mémoire et bind mounts).

La limite de taille multipart est effective par requête, ainsi que les limites de pixels et de
champs. En revanche, aucun plafond applicatif du nombre de uploads simultanés, du nombre de
jobs en attente ou des octets persistants cumulés n'a été trouvé. Aucun délai maximal de
réception de corps n'est défini ici. Les routes JSON passent par la lecture complète du corps
FastAPI avant validation, sans budget analogue à celui du multipart.

Preuve bornée : PUT dispatch avec un champ inconnu de **1 048 576 octets** : **422**, après
lecture/analyse du corps, sans rejet anticipé de taille. Aucun envoi massif ni épuisement mémoire
n'a été provoqué. La saturation par concurrence reste une conséquence de l'absence de plafonds,
pas un épuisement démontré pendant l'audit.

Impact : accumulation de corps/spools, décodages concurrents et stockage de sources acceptées
lorsqu'aucun worker ne les consomme. Les limites RAM des conteneurs bornent leur mémoire mais
pas les bind mounts sur le disque hôte. La rétention ne purge pas les QUEUED, ni les protégées.
Un client autorisé ou une soumission cross-site peut donc aussi épuiser le service.

**À faire** : plafond JSON avant parsing et limite de corps au point d'entrée ; admission bornée
avant parsing des uploads (429/503), délai de réception, quota de jobs/octets et marge disque.
Les réservations doivent tenir compte des uploads concurrents et de l'image normalisée, plutôt
qu'un simple contrôle d'espace libre isolé sujet aux courses. Vérifier ces bornes avec de petits
budgets injectables, sans test destructif sur le stockage réel.

### SEC-03 — lectures agrégées sans borne — moyenne

Sources : `api/resources.py:496` (`/queue`), `api/resources.py:438` (`/logs`),
`api/resources.py:230` (`/system/status`).

`/queue` renvoie toutes les générations actives avec représentation complète et requêtes
additionnelles par élément. Mesure reproductible sur la base temporaire, distribution suspendue :

| Générations retournées | Requêtes SQL | Octets de réponse |
|---|---:|---:|
| 21 | 43 | 13 605 |
| 41 | 83 | 26 465 |

Aucun gros volume n'a été créé. La mesure confirme l'amplification linéaire et l'absence de
pagination, pas un blocage à ces petites tailles. Le polling UI prévu toutes les 2 secondes
accentuera le coût d'une file durablement remplie.

`/system/status` parcourt aussi les générations et résultats ; `/logs?tail=1` itère sur tout
le journal via deque, et une ligne n'est pas bornée en octets. Les journaux sont produits par
un composant de confiance : ce dernier point n'est pas présenté comme une injection distante.

**À faire** : file paginée ou projection compacte bornée, requêtes groupées, compteurs SQL,
mesure de stockage mise en cache et lecture arrière de journaux avec budget d'octets.

### SEC-04 — avis npm dans l'outillage de développement — modérée, développement uniquement

`node_modules/@typescript-eslint/typescript-estree/node_modules/minimatch` est verrouillé en
**10.2.6**. L'avis [GHSA-g3hv-75wg-m249 / CVE-2026-118764](https://github.com/advisories/GHSA-g3hv-75wg-m249)
concerne une amplification CPU/mémoire par motif glob contrôlé ; versions affectées >=7 et <11.0.1,
correctif annoncé en 11.0.1. L'avis vise notamment optimizationLevel >=2.

npm audit rapporte **8 entrées modérées pour un même avis racine**, propagé via typescript-eslint
et eslint-config-next. Ce ne sont pas huit vulnérabilités indépendantes.
`npm audit --omit=dev` : **0 avis**. Aucun chemin HTTP du produit vers un glob minimatch contrôlé
par un utilisateur n'a été établi. Le risque constaté concerne lint/build/CI.

**À faire** : mise à niveau compatible de la chaîne concernée ou override ciblé après validation.
Ne pas lancer `npm audit fix --force` : la proposition observée rétrograde eslint-config-next
vers une autre majeure. Rejouer lint, types et build frontend après correction.

### SEC-05 — métadonnées originales et routes de preuve P0 — faible / confidentialité

Sources : `api/resources.py:400`, `imaging.py:61`, `frontend/src/app/p0/probeFile.ts:22`.

L'image d'inférence est débarrassée des métadonnées ; l'original est conservé et servi tel quel.
Preuve : marqueur EXIF synthétique `SECURITY_AUDIT_TEST` toujours présent dans la réponse
`/source` (200). C'est conforme au contrat actuel « original », mais des coordonnées GPS peuvent
être présentes dans une vraie photo. L'accès doit être protégé et le partage via P3 explicite.
Préférer l'image normalisée pour l'affichage/partage, avec accès distinct à l'original si conservé.

Les routes P0 servent deux noms fixes, sans chemin fourni par l'appelant ; pas de traversée
HTTP identifiée. Leur erreur 404 révèle toutefois le chemin de répertoire de sonde. Retirer ou
réserver ces routes au développement lors du packaging P3, et utiliser un message générique.

## Contrôles favorables et limites de confiance

- Identifiants ULID canoniques, chemins reconstruits depuis des noms fixes, relative_path SQL
  ignoré au téléchargement ; symlinks statiques refusés. Pas de SQL utilisateur interpolé ni
  d'exécution shell/eval issue de paramètres HTTP identifiée.
- Baux clôturés/expirés et anciennes tentatives refusés ; promotion et transition sous verrou,
  suppression en trois phases, contrôle conditionnel de la rétention. Pas de contournement
  distant de ces contrôles identifié pendant cette revue.
- Images décodées par format réel, plafond de pixels avant décodage complet, normalisation EXIF,
  seeds/paramètres validés, fermeture des spools en erreur.
- Rootfs ro, utilisateur non root, capabilities retirées, no-new-privileges, poids ro,
  services offline, profils GPU explicites, contexte de build en liste d'inclusion, CI à droits read.
- Recherche de motifs de clés usuelles sur les fichiers suivis : aucun match. Ce contrôle ne
  couvre pas toutes les formes de secrets et n'analyse pas les fichiers locaux ignorés.
- Les vérifications Path puis FileResponse ne constituent pas une ouverture atomique contre un
  processus local qui modifierait le filesystem entre contrôle et ouverture. Aucun vecteur HTTP
  permettant cette substitution n'a été établi ; envisager des ouvertures par descripteur et
  O_NOFOLLOW si ce modèle de menace doit être couvert.
- Le worker, le SDK et le stockage partagé restent des composants de confiance. Le durcissement
  des conteneurs ne constitue pas une sandbox pour exécuter des modèles/code tiers hostiles.

## Résultats des outils

| Contrôle | Résultat / portée |
|---|---|
| pip-audit API | 32 dépendances, aucun avis connu, aucun paquet ignoré |
| pip-audit worker | 88 entrées, aucun avis sur les entrées auditées ; Idol Git, torch+cu132 et torchvision+cu132 ignorés par l'outil |
| Audit complémentaire versions amont | torch 2.14.1 / torchvision 0.29.2 sans suffixe : aucun avis ; ne certifie pas les binaires CUDA |
| npm audit complet | 8 entrées modérées, un avis racine minimatch |
| npm audit production | 0 avis connu |
| Bandit | 5 002 lignes ; B310 sur URL de santé fixe, 6 B101 sur assertions internes du superviseur |

B310 n'établit pas de SSRF : l'URL est une constante HTTP locale, non fournie par l'appelant.
Les assertions B101 examinées protègent des invariants internes, pas l'identification ni les
validations des entrées HTTP. Ces alertes ne sont pas assimilées à sept failles confirmées.

Commandes de collecte :

```bash
cd backend
uv export --frozen --no-dev --no-emit-project --no-hashes --format requirements.txt --output-file /tmp/api-requirements.txt
uvx --from pip-audit pip-audit --no-deps --disable-pip -r /tmp/api-requirements.txt --format json
# Même export avec --extra idol pour le worker ; ne résout/installe pas torch.
uvx --from bandit bandit -r src -f json
cd ../frontend
npm audit --package-lock-only --ignore-scripts --json
npm audit --package-lock-only --ignore-scripts --omit=dev --json
```

L'absence d'avis au moment du scan ne prouve pas l'absence de vulnérabilité. Aucun scan des
paquets système Debian, bibliothèques CUDA natives, shaders/wasm, pilote ou noyau n'a été réalisé.
Le SDK Git Idol n'a pas été audité intégralement. Aucun fuzzer de décodeur d'image ni chaîne
navigateur/PNA/CSRF complète n'a été exécuté. Le futur frontend/proxy P3 n'existe pas encore :
une revue de son intégration sera nécessaire avant exposition.

## Suite recommandée

1. Traiter SEC-01 et SEC-02 avant toute publication HTTP du frontend/proxy.
2. Borner les lectures SEC-03 lors du raccordement du polling UI.
3. Corriger SEC-04 avec validation de la chaîne frontend ; intégrer un contrôle d'avis en CI.
4. Décider le traitement des originaux et supprimer/neutraliser les sondes P0 en production.
5. Rejouer les reproductions négatives et les tests avant d'ouvrir P3 à des utilisateurs.

P2 demeure validée fonctionnellement. P3 n'a pas été commencé ; les mesures ci-dessus constituent
le travail de sécurité à décider/appliquer avant son exposition. Aucun commit, push, déploiement
ou modification d'un service existant n'a été effectué pendant l'audit.
